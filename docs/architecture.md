# Architecture

How the program is put together, for anyone changing it. For what changed and
when, see [`CHANGELOG.md`](../CHANGELOG.md); for what's next, see
[`roadmap.md`](roadmap.md).

## Why a rewrite?

The original oneko (and most clones) rely on X11 tricks — override-redirect
windows and the SHAPE extension — that don't work under Wayland compositors like
Hyprland. This version uses:

- **`wlr-layer-shell`** (via [smithay-client-toolkit](https://crates.io/crates/smithay-client-toolkit))
  for an always-on-top overlay surface
- **ARGB transparency** instead of the X11 SHAPE extension
- **Hyprland's IPC socket** to track the cursor globally, behind a
  `CursorSource` trait so other compositors can be plugged in
- A **small input region matching the cat's 32×32 box**, so it can catch clicks
  to toggle freezing without stealing focus or blocking anything outside its own
  bounds

| file | what |

| `moments.rs` | the random phrase/quirk table — add phrases here |
| `sprites.rs` | skin/pose types and lookup; the art itself is generated by `build.rs` |
| `xbm.rs` | the XBM decoder, shared by `build.rs` and the runtime skin loader |

## The event loop

Two sources feed one calloop loop: the Wayland socket and an animation timer.

The Wayland socket is watched continuously, so pointer clicks and output hotplug
are handled the moment they arrive — click-to-freeze is instant no matter how
slow the animation tick is running.

The timer drives motion. Its interval is not fixed: it comes from `--fps`, and
stretches to 250 ms once the cat is asleep, since nothing on screen is changing
and there's no reason to poll the cursor at motion rate to find that out.

Each tick reads the cursor once, works out which monitor contains it, animates
only that monitor's cat, and hides the rest. A frame that would be
pixel-identical to what's already on screen is skipped entirely — no SHM
allocate, blit, damage or commit.

## Timing

**Every duration is wall-clock, not a count of ticks.** This matters because the
tick interval varies. Tick-counted thresholds would silently rescale the cat's
whole behavior whenever the rate changed, so "sit after 3 ticks" is "sit after
375 ms" instead. The constants are the old tick counts × the original 125 ms, and
a test pins that equivalence.

**Motion rate and animation rate are independent.** Position updates every tick;
the two-frame walk cycle advances on its own fixed 8 Hz clock. The walk cycle is
only two frames, so flipping it once per tick was fine at 8 ticks/second but
strobes at 60 — the cat would vibrate rather than walk.

**Chase speed is framerate-independent.** The easing is exponential decay over
elapsed time, not a fixed fraction per tick, so splitting a step into N smaller
steps lands the cat in exactly the same place. At 125 ms it reproduces the
original `* 0.3` exactly.

## Cursor tracking

Wayland deliberately doesn't expose the pointer position outside your own
surfaces, so there is no portable way to ask where the mouse is — every
compositor needs its own answer. That's what `CursorSource` abstracts:

```rust
pub trait CursorSource {
    fn position(&mut self) -> Option<(f32, f32)>;
    fn name(&self) -> &'static str;
}
```

Supporting a new compositor means writing one implementation and adding one line
to `detect()`. Nothing else in the program changes.

`position()` returning `None` must mean "no answer", never a fallback
coordinate: callers skip the tick rather than moving the cat. A made-up `(0, 0)`
is a real on-screen point on any layout with negative monitor offsets, so it
can't even be recognised as bogus downstream.

The one implementation today is `HyprlandIpc`, which reads `cursorpos` from
Hyprland's IPC socket. Both socket locations are probed
(`$XDG_RUNTIME_DIR/hypr/…` and the older `/tmp/hypr/…`) so one binary works
across Hyprland versions.

## Sprites and skins

Art lives in [`assets/skins/`](../assets/skins) as real `.xbm` files.
`build.rs` compiles every skin there into the binary as `[u8; 128]` arrays — the
same runtime representation as the hand-written hex it replaced, at the same
cost. `src/xbm.rs` holds the decoder and is `include!`d by `build.rs`, because a
build script can't `use` the crate it builds and two copies of a parser drift.

The same decoder loads user skins from `~/.config/oneko-rust/skins/` at startup,
so a directory that builds in also works as a user skin.

Poses are addressed by a `Pose` value rather than a sprite reference. The dirty
check compares poses, which is both cheaper and exact — comparing
`&'static [u8; 128]` pointers would have been silently wrong, since LLVM's
constant-merging pass may unify two byte-identical consts.

See [`assets/README.md`](../assets/README.md) for the pose list, the mask
convention, and how to author a skin.
